How the agent operates this business unattended — Telegram, the queue, the site, delegation rules, and the traps that already cost a run.

Working mode

Nightshift (~/work/nightshift) runs this project unattended, round after round. Each round is a fresh context. Matt reads two things and nothing else: Telegram messages, and HTML pages on the preview site. He is usually on a phone. He does not read code, local files, or terminals.

The single goal

The fastest first EUR 1 from a paying stranger. Not a salary model, not an audience, not a book. Judge every decision by how much it shortens that path.

The rule about verdicts

Matt's standing instruction: assume a viable angle exists and find it. Concluding "not viable" almost always means we were too strict or considered too few options. If a path is blocked, name the next-nearest path.

Talking to Matt

chat.jsonl (project root) is the whole conversation, both directions: one {ts, from, text} object per line, oldest first, append-only. from is matt, agent (you, earlier) or harness (the driver). Read the tail every round, before anything else:

tail -n 20 chat.jsonl | jq -r '"\(.from): \(.text)"'

A matt line after the last agent line is unanswered. Answer it and treat it as him speaking. harness lines do not count.

Speaking is one action, and the only way to speak:

~/work/nightshift/bin/notify.sh "your text"

It appends to chat.jsonl and sends to Telegram. Never write to chat.jsonl by hand.

The trap: the run stops when QUEUE.json has nothing active and the last speaker was you. Speaking closes the conversation. Put every outstanding thing in the queue before you send anything — a "working on it" message with an empty queue ends the run.

When to speak: blocked with a real question, or something big is finished or unlocked. Not status noise. Never send a long status wall in reply to a bare greeting — that was sent verbatim across four rounds and Matt never engaged with one. A greeting gets a short menu of what he can ask for.

There is no Artifact tool in this session. The only way to show Matt a page, a table or a long document is the preview site.

The site is the second channel

The whole preview site is generated from docs/ + data/ by bin/build_site.py, and pushed by bin/publish.sh. Hub, canonical docs, decision log, research notes, session log and the queue are all pages on it. Live at https://mattia-palmieri.github.io/engine-room-press-preview/.

Run bin/publish.sh at the end of any round that changed a doc or a deliverable. A Telegram message with no updated page behind it is half a report. Never hand-edit data/site/ — it is wiped on every build.

What Matt does himself

  • Accounts he runs: Instagram, TikTok, Pinterest, Reddit, X, Medium, Substack, a blog, Amazon KDP, Gumroad/Stripe. The agent drafts and generates; Matt pastes and posts.
  • His time budget: 3–5 hours a week. Enough to post regularly, reply to comments, and quality-check drafts. Not enough for daily manual production. Every manual step must justify itself against that budget.
  • Publish nothing, buy nothing, touch no account. Domain purchase is approved in principle but Matt buys it himself — the agent only shortlists and checks availability.

Delegating research — rules that came from a failure

The first market-living run was marked done on a file where 84 numbers were model-memory guesses labelled "(unverified)". A full re-run to fix. The cause was a budget squeeze plus no check at the end.

  1. Never paraphrase a source doc into a subagent prompt. Tell it to read docs/notes/source-access.md itself. Prompts that summarised the recipe failed; prompts that said "read the file" worked.
  2. Never offer "mark it unverified" as an escape hatch. Say: never invent a number; if you cannot fetch it, write not found and footnote what you tried. An honest gap beats a guess; a guess poisons every decision downstream.
  3. A task never marks its own fan-out done. A separate QA step reads the literal done_when, greps the output for hedge words, and refetches a random sample to confirm the numbers are real. Only then flip the status.
  4. A subagent that spawns children cannot wait on them. It returns "my children are running" and exits. Either fan out from this level, or message the parent again once the children's files land and tell it to compile now. This has already happened twice in one run.

Model choice: Sonnet by default. Haiku only for cheap mechanical scans. Opus only for real reasoning. Have subagents write to a file, not report prose.

Operational traps, already paid for

  • rb is one shared Chrome daemon. Parallel browser subagents hijack each other's navigation mid-flight, and a hijack reads exactly like real data. One browser subagent per round. Always confirm the URL that actually loaded.
  • Amazon needs no warm-up. Cold deep links work; cookie freshness on disk (~/.agent-browser/profiles/real-browser) is what matters, not keeping the browser open.
  • Amazon sales rank is per edition. The same book can be #515 in one format and #62,645 in another. Never compare rank across formats.
  • Headless Chrome card renders need --virtual-time-budget=6000. Google Fonts load over the network; without the wait, type silently falls back to system sans and the render looks fine but is wrong.
  • python3 -m markdown needs --break-system-packages --user, and build_site.py adds the user site-packages path itself so it works headless.
  • Heredocs can hang in the interactive cmux shell. Write the script to a file first.
  • Nothing under ~/Documents, ~/Desktop or ~/Downloads. A macOS permission dialog on a binary in those folders froze an unattended round for 43 hours. That is why the project lives at ~/work/history-books. A stall watchdog now kills a round with no log growth for 900s.

Cost

There is no per-round cap. One was tried ($2.00) and it broke the first research round — the squeeze is what made subagents guess numbers instead of fetching them. If a cap is ever restored, NIGHTSHIFT_MAX_USD (~$5) is the setting and it is Matt's to change. Never shrink the research to fit a cap; stop and say so.
